# J.A.R.V.I.S. v0.2.0 Optimization Architecture

Status: design specification approved in principle · 2026-09-15

## 1. Purpose

J.A.R.V.I.S. v0.2.0 is an evidence-driven optimization release. Its objective is not maximum autonomy, minimum latency, or minimum cost in isolation. The system should maximize **verified usefulness per resource unit** while preserving explicit authority, bounded risk, reproducible evidence and honest uncertainty.

The release will optimize the runtime, cognitive control plane, context economy, memory, routing, execution, verification, observability, HUD, CI, repository structure, documentation and public product surfaces as one coherent system.

## 2. Compatibility policy

The project adopts a hybrid compatibility model:

- preserve important public entry points and workflows when they remain useful;
- permit internal breaking changes when they materially improve correctness, modularity or evidence quality;
- version persisted schemas and provide explicit migrations for durable state;
- use compatibility adapters where a public contract must survive while internals change;
- remove obsolete legacy behavior only after equivalent or better behavior is demonstrated by tests and evidence;
- never move or retarget the immutable `v0.1.0` tag.

Compatibility exists to protect users and evidence, not to preserve accidental internal architecture indefinitely.

## 3. Current baseline

The current `main` already provides:

- zero-dependency Python launcher and local HTTP server;
- local HUD in vanilla HTML/CSS/JavaScript;
- governed skill registry and distribution tooling;
- mission/task/attempt models, DAG execution, policy, scheduler, recovery and persistence primitives;
- bounded provider/model routing and inference primitives;
- context governor, cognitive governor and memory components in partial integration;
- verification structures and explicit execution/verification/outcome distinctions;
- canonical design system, `DESIGN.md` and `AGENTS.md`;
- cross-platform CI and SSP repository audit;
- immutable public v0.1.0 release evidence.

The roadmap still marks important whole-system behavior as `PARTIAL` or `PLANNED`. v0.2.0 must close the highest-value gaps instead of hiding them behind UI or documentation.

## 4. Architectural principles

### 4.1 Evidence before claims

Execution success, verification success, recovery state and mission outcome remain independent state axes. HTTP 200, process exit code 0, tool completion or model text do not imply a verified outcome.

### 4.2 Authority before autonomy

The runtime may optimize only inside explicit authorization, scope, budget, effect and policy boundaries. Missing authority is not permission. Unknown mutable effects are not safe to retry automatically.

### 4.3 Adaptive optimization

The Cognitive Governor arbitrates between autonomy, cost, latency, confidence and verification rigor according to task risk and available evidence. No single metric dominates globally.

### 4.4 Honest unknowns

Unknown cost, latency, token usage, risk, provenance or effect state is represented as `UNKNOWN` or an equivalent explicit state. Unknown is never silently converted into zero, success or low risk.

### 4.5 Progressive disclosure

Context is loaded in layers: catalog, manifest, targeted source, broader source. Required context cannot be silently omitted to satisfy a budget.

### 4.6 Small, replaceable units

Each subsystem owns one responsibility, has a narrow interface and emits structured receipts. Internal implementations may evolve without forcing consumers to understand their internals.

## 5. Target architecture

The optimized runtime is organized into eight cooperating planes.

### 5.1 Trusted Runtime Core

Owns durable contracts and safety-critical state:

- mission, task and execution-attempt schemas;
- authorization grants and scope digests;
- effect declarations and idempotency semantics;
- atomic state transitions and restart-safe persistence;
- artifact and evidence references;
- budgets and resource receipts;
- failure classification and attribution;
- recovery, reconciliation and compensation state.

A task is not dispatchable until admission proves that its required authority, dependencies, effects, resource policy and verification strategy are sufficiently defined.

### 5.2 Cognitive Governor

The Governor chooses strategy but never performs effectful work directly. It may decide:

- whether more context is justified;
- whether to escalate model/tool capability;
- whether to retry, reconcile, replan or stop;
- whether an observation is eligible for memory admission;
- how to allocate remaining resource budget;
- when human intervention is required.

The optimization objective is conceptually:

```text
maximize verified_utility
subject to authority, risk, budget, latency and confidence constraints
```

No aggregate score may mix heterogeneous resource units without explicit normalization and versioned weights.

### 5.3 Context Economy

Introduces a first-class `ContextReceipt` for each material context decision. A receipt records at minimum:

- mission/task identity;
- candidate sources considered;
- sources admitted and omitted;
- selection reason;
- source identity/hash;
- serialized bytes;
- token estimate when available, including estimation method;
- freshness/provenance;
- cache status;
- required-context flags;
- budget before and after admission.

Context compression is allowed only when constraints, authority and required evidence remain intact.

### 5.4 Memory Fabric

Separates memory into working, episodic, semantic and procedural classes.

Durable memory admission requires provenance, freshness and an admission reason. Unverified output may be retained as an episode, but must not silently become a verified semantic fact or trusted procedure.

Memory retrieval emits a `MemoryReceipt` describing what was considered, selected, rejected and why.

### 5.5 Routing Plane

Model, tool and skill selection uses explicit capabilities, policy, environment compatibility, measured historical evidence and current budgets.

Fallback is a policy decision with a reason, not an implicit `except` path. A selected profile is not proof that an executable adapter exists; adapter binding is verified separately.

Routing emits a `DecisionReceipt` containing candidates, exclusions, policy reasons, selected capability, confidence method and expected resource class.

### 5.6 Execution and Verification Plane

Every effectful action produces an `ExecutionReceipt` linked to a durable attempt. Verification produces a distinct `VerificationReceipt`.

The execution plane records:

- adapter/tool identity;
- input and environment fingerprints;
- start/end timestamps;
- actual or unknown usage;
- artifacts;
- declared and observed side effects;
- failure class;
- reconciliation requirement.

The verification plane records independent requirements, evidence, verifier identity/method and the resulting verification state.

### 5.7 Observability Plane

Decision, context, memory, execution and verification receipts form a correlated timeline by mission/task/attempt/trace identifiers.

The timeline is the primary diagnostic surface for:

- debugging;
- performance analysis;
- cost/context analysis;
- restart/recovery inspection;
- demo and release evidence;
- HUD rendering.

Private chain-of-thought is not an observability dependency. The system exposes structured decisions, evidence and outcomes instead.

### 5.8 Experience Plane

The canonical `design-system/` remains the visual source of truth. The HUD evolves into an operational cockpit rather than a decorative dashboard.

Primary views should expose real runtime state:

- mission graph and current objectives;
- running, blocked and reconciliating attempts;
- context budget and admitted sources;
- routing decisions and capability exclusions;
- verification/evidence state;
- memory admissions and retrievals;
- cost/latency/resource receipts when measured;
- Operational Progression derived only from real telemetry.

When a metric is unavailable, the HUD renders an explicit unknown state instead of invented data.

## 6. Optimization strategy

Implementation follows incremental rearchitecture, not a rewrite.

### Phase 1 — Contract closure

Close P0 correctness gaps in durable attempts, grants, effects, idempotency, restart safety, reconciliation, failure semantics and resource accounting.

Exit condition: effectful work cannot bypass the trusted attempt/admission path.

### Phase 2 — Receipt model

Introduce versioned decision/context/execution/verification/memory receipts with stable correlation identifiers.

Exit condition: a deterministic mission can be reconstructed from structured receipts without reading internal logs.

### Phase 3 — Adaptive Governor

Bind the Cognitive Governor to real budgets, receipt history, confidence and stop/escalation policies.

Exit condition: deterministic tests prove continue, expand-context, escalate, replan, stop and human-intervention decisions under bounded fixtures.

### Phase 4 — Context and memory economy

Integrate progressive disclosure, freshness-aware caching, admission/retrieval policies and memory provenance.

Exit condition: repository-scale fixtures demonstrate bounded admission without silently dropping required context.

### Phase 5 — Empirical routing

Connect tool/model/skill routing to measured capability and resource evidence while preserving policy-first exclusion.

Exit condition: deterministic fixtures demonstrate why candidates were excluded and why the selected route was admitted.

### Phase 6 — HUD operational cockpit

Render the new receipt/timeline model using the canonical design system, preserving important existing navigation contracts through adapters where practical.

Exit condition: browser smoke validation proves core HUD routes render real fixture state in dark/light themes with no fabricated telemetry.

### Phase 7 — CI and benchmark architecture

Separate validation responsibilities into clear gates:

- unit tests;
- contract tests;
- integration tests;
- restart/recovery tests;
- deterministic provider tests;
- HUD/browser smoke tests;
- benchmarks;
- release-evidence checks.

Exit condition: each release claim maps to a named machine-verifiable artifact or gate.

### Phase 8 — Documentation and repository consolidation

Reconcile README, roadmap, architecture docs, vault projections and historical reports. Historical evidence remains available but is explicitly labeled historical where superseded.

Exit condition: no current document claims stronger whole-system behavior than the corresponding tests and release evidence prove.

### Phase 9 — Public product and v0.2.0 release

Complete the reproducible demo, repository-scale benchmark, deterministic provider fixture, contributor onboarding and v0.2.0 evidence bundle.

The release may progress through release candidates. Final v0.2.0 is published only when every mandatory gate is green.

## 7. Persistent schema and migration policy

Any durable schema change must include:

- explicit schema version;
- deterministic migration or explicit unsupported-version rejection;
- preservation of uncertainty from legacy records;
- migration tests using representative older fixtures;
- no synthesis of authoritative identifiers or evidence that did not exist in the source record.

Legacy compatibility data may be projected through adapters, but the canonical internal model should not inherit ambiguous defaults solely for backward compatibility.

## 8. Error and recovery semantics

Failures are classified separately from blame/attribution. At minimum the runtime distinguishes policy, authorization, validation, integrity, dependency, transient external service, permanent external service, timeout, conflict, cancellation, exhausted resource, malformed input and unknown failure.

Retries require evidence that retry semantics are safe. A timeout after a potentially mutable external action enters reconciliation unless the adapter can prove the effect did not occur.

Compensation is an independent authorized attempt with its own policy, effects, evidence and verification.

## 9. Testing architecture

### Unit tests

Validate pure rules, serialization, scoring, budgeting and small state transitions.

### Contract tests

Validate public and durable interfaces, schema compatibility, fail-closed behavior and invariants between subsystems.

### Integration tests

Prove planner/resolver/governor/adapter/runtime/verification interactions with deterministic fixtures.

### Restart and recovery tests

Persist work, terminate the process, restore state and prove that duplicate mutable effects are not issued without reconciliation/idempotency evidence.

### Deterministic provider tests

Use a provider-neutral mocked transport that proves the adapter was actually invoked and that transport success does not imply verification.

### Browser/HUD tests

Exercise the served runtime routes, navigation, sidebar persistence, design-system showcase and representative receipt views. The browser layer tests presentation and interaction, not domain correctness already covered below it.

### Benchmarks

Benchmarks must publish raw measured units and methodology. Serialized-byte reductions are not converted into token, cost, latency or quality claims unless independently measured for that dimension.

## 10. v0.2.0 release gates

Final v0.2.0 requires all of the following:

1. Portable runtime matrix green on Windows, Ubuntu and macOS.
2. Full unit/contract/integration test battery green.
3. Restart/recovery/idempotency fixtures green.
4. Deterministic provider fixture green.
5. Browser/HUD smoke validation green.
6. Repository-scale context benchmark with machine-readable output.
7. Resource measurements represented as measured values or explicit unknowns.
8. Release evidence bundle generated from the exact candidate commit.
9. Documentation claim audit green.
10. Immutable v0.1.0 tag unchanged.

If any mandatory criterion is unproven, the candidate remains an RC and is not promoted to final v0.2.0.

## 11. Public API policy

The following are treated as high-value compatibility surfaces unless a later migration explicitly supersedes them:

- `python jarvis.py` launcher flow;
- `--doctor`, `--test` and `--full-test` validation entry points;
- local HUD startup behavior;
- canonical skill-registry layout and contribution path;
- release evidence semantics;
- important public HTTP/HUD routes where existing users reasonably depend on them.

Internal module layout, private helpers and provisional schemas may change when adapters/migrations protect durable consumers.

## 12. Non-goals for v0.2.0

This release will not:

- claim general AGI or unrestricted autonomous operation;
- optimize by bypassing authorization or verification;
- add a second scheduler, goal engine, memory system or governor merely to match naming conventions;
- require a frontend framework migration solely for aesthetics;
- convert byte benchmarks into token/cost claims without measurement;
- enable broad external-effect integrations before the local trusted runtime proves their admission and recovery semantics;
- remove historical evidence that remains useful for auditability.

## 13. Success criteria

v0.2.0 succeeds when a user can run a bounded mission and inspect a coherent, restart-safe chain showing:

1. what goal was admitted;
2. what context was considered and loaded;
3. which route was selected and why;
4. which adapter actually executed;
5. what resources were measured or remained unknown;
6. what side effects occurred or require reconciliation;
7. what independent evidence verified the result;
8. what memory, if any, was admitted afterward;
9. why the Governor continued, escalated, replanned or stopped;
10. the same facts rendered truthfully in the HUD and release evidence.

That chain, not feature count, is the core product improvement of J.A.R.V.I.S. v0.2.0.
