# J.A.R.V.I.S. v0.2.0 Implementation Master Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Deliver J.A.R.V.I.S. v0.2.0 as an evidence-driven optimization release whose runtime, Governor, context/memory economy, routing, observability, HUD, CI and release process all expose truthful, correlated evidence.

**Architecture:** Incremental rearchitecture. Preserve useful public entry points while allowing internal breaking changes behind migrations/adapters. Every implementation phase starts from a green `main`, uses TDD, lands through its own PR, and becomes the base for the next phase only after post-merge validation.

**Tech Stack:** Python 3.12 standard library runtime; vanilla HTML/CSS/JavaScript HUD; Node built-in test runner where already used; PowerShell legacy governance; GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-09-15-jarvis-v0.2.0-optimization-design.md`

## Global Constraints

- Never move or retarget immutable `v0.1.0`.
- Preserve `.github/workflows/release.yml` and `.github/workflows/publish-v0.1.0-tag.yml` as v0.1.0-specific evidence machinery.
- Do not add a second scheduler, planner, memory fabric, Cognitive Governor, model router or tool router when the existing subsystem can be extended.
- Execution, verification, recovery and mission outcome remain separate state axes.
- Unknown resource usage is `UNKNOWN`, never silently zero or estimated unless the estimation method is explicit.
- Policy/authority filters run before optimization/ranking.
- Required context cannot be silently omitted to satisfy a budget.
- Durable schema changes require explicit versioning and deterministic migration/rejection tests.
- No private chain-of-thought is required for observability; receipts expose decisions, evidence and outcomes.
- The zero-dependency runtime requirement applies to shipped runtime code. Test-only browser dependencies may be introduced later if pinned and isolated.
- Every user-facing metric must come from real fixture/runtime data or render an explicit unknown/no-data state.

## Branch and PR Discipline

For each implementation plan:

1. Confirm `main` equals the latest green post-merge commit.
2. Create a fresh branch from that exact `main`.
3. Add focused RED tests first and execute them to prove the intended failure.
4. Implement the smallest coherent change that makes those tests GREEN.
5. Run focused tests, then `python run_tests.py`, launcher gates and relevant benchmark/audit commands.
6. Open a PR with problem/change/evidence/boundary/risk.
7. Merge only after required GitHub Actions are green.
8. Re-run/inspect post-merge `main` workflows before starting the next plan.

Do not stack phase 2 on an unmerged phase 1 branch. This prevents hidden coupling and keeps bisect/revert practical.

## Phase Gates

### Gate A — Trusted Runtime

Plan 1 is complete only when:

- resource accounting distinguishes measured/estimated/unknown/not-applicable;
- token charging no longer invents USD cost;
- durable state migration preserves uncertainty and rejects unsupported future schemas;
- authorization is bound to immutable action/scope/budget context with expiry/revocation checks;
- execution and verification receipts correlate with durable attempts;
- restart/recovery tests prove ambiguous mutable effects are not duplicated.

### Gate B — Adaptive Cognition

Plan 2 is complete only when:

- ContextReceipt separates serialized bytes from optional token estimate;
- memory provenance/freshness cannot silently promote unknown data to trusted semantic/procedural memory;
- Governor deterministically emits CONTINUE / EXPAND_CONTEXT / ESCALATE_CAPABILITY / REPLAN / STOP / REQUIRE_HUMAN;
- model/tool/skill routing applies hard constraints before empirical ranking;
- unresolved skills/capabilities remain explicitly unresolved instead of synthetic success candidates.

### Gate C — Observability and HUD

Plan 3 is complete only when:

- receipts are append-only/queryable by mission/task/attempt/trace;
- mission timelines can be reconstructed without internal logs;
- read-only server APIs expose summaries/timelines;
- the HUD renders mission, attempts, context, routing, evidence, memory and resource state using the canonical design system;
- no-data/unknown is not rendered as 0 or 100%;
- current public HUD routes/navigation stay usable.

### Gate D — Validation Architecture

Plan 4 is complete only when:

- deterministic provider tests prove actual invocation and failure semantics without network/API keys;
- restart/recovery fixtures are explicit CI gates;
- repository-scale context benchmark emits machine-readable raw units;
- browser/HUD smoke validates served pages/interactions;
- CI separates contract/integration/recovery/browser/benchmark claim responsibilities;
- documentation claim audit rejects unsupported current claims.

### Gate E — Release

Plan 5 is complete only when:

- a separate v0.2.0 release workflow validates an exact candidate SHA/tag;
- the evidence bundle includes all mandatory gates and raw artifacts;
- README/Quickstart/demo claims are updated only from passed evidence;
- RC promotion refuses final release while a mandatory gate is absent or unproven;
- v0.1.0 tag/workflows remain unchanged.

## Baseline Validation Commands

Every phase runs at least:

```bash
python run_tests.py
python jarvis.py --doctor
python jarvis.py --test
python benchmarks/context_budget_benchmark.py
python tooling/audit_pre_publish_security.py
```

UI/server phases additionally run:

```bash
node --test tests/test_chat_session.cjs
```

When browser smoke is introduced, its pinned test command becomes a mandatory additional gate.

## Commit Strategy

Prefer one commit per proven behavior cluster, for example:

```text
test: define honest resource measurement contracts
feat: add measured resource accounting

test: define durable grant lifecycle
feat: bind execution authorization grants

test: define receipt correlation contracts
feat: persist execution and verification receipts
```

Never combine unrelated formatting or opportunistic refactors with a contract-closing commit.

## Completion Definition

The initiative is complete only when a bounded mission can be inspected end-to-end as a correlated chain showing admission, context, routing, actual adapter execution, measured/unknown resources, effects/recovery, independent verification, memory admission and Governor continuation/stop reasoning, and those same facts are rendered truthfully in the HUD and exact-commit release evidence.
