# J.A.R.V.I.S. v0.2.0 Release + Productization Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task.

**Goal:** Build a separate evidence-gated v0.2.0 RC/final release path, generate exact-commit evidence, update public product surfaces from measured results, and publish final v0.2.0 only when every mandatory gate is proven.

**Architecture:** Keep all v0.1.0 tag/workflows immutable. Add a v0.2.0-specific evidence builder and release workflow that validates an exact SHA/tag, gathers already-established CI/benchmark/browser/claim evidence, refuses promotion when a mandatory artifact is absent, and supports prerelease RCs before final promotion.

**Tech Stack:** GitHub Actions, Python 3.12 stdlib, existing PowerShell packaging/governance, GitHub Releases.

**Spec:** `docs/superpowers/specs/2026-09-15-jarvis-v0.2.0-optimization-design.md`

## Preconditions

- Plans 1–4 merged and green.
- `main` has named contract/integration/recovery/provider/browser/benchmark/claim gates.
- Repository-scale benchmark and evidence manifest are stable.
- No final version claims have been published prematurely.

## Task 2 — Promotion Gate

**Files:**
- Create: `tooling/check_v020_release_candidate.py`
- Create: `tests/test_agentic_v020_release_promotion.py`

Interface:

```bash
python tooling/check_v020_release_candidate.py \
  --evidence release-artifacts/v0.2.0/release-evidence.json \
  --channel rc

python tooling/check_v020_release_candidate.py \
  --evidence release-artifacts/v0.2.0/release-evidence.json \
  --channel final
```

Rules:
- RC may preserve explicitly documented empirical gaps that are not mandatory final gates;
- final requires every mandatory v0.2.0 gate PASS;
- exact SHA/tag consistency is mandatory for both;
- unsupported/missing evidence schema fails closed;
- `v0.1.0` immutable target mismatch fails both.

Commit: `feat: fail closed on incomplete v0.2.0 promotion evidence`

## Task 3 — Separate v0.2.0 Release Workflow

**Files:**
- Create: `.github/workflows/release-v0.2.0.yml`
- Do not modify: `.github/workflows/release.yml`
- Do not modify: `.github/workflows/publish-v0.1.0-tag.yml`

Workflow is `workflow_dispatch` first and accepts:

```text
tag
expected_sha
channel: rc | final
```

It must:
1. validate tag format (`v0.2.0-rc.N` for RC, `v0.2.0` for final);
2. checkout the exact tag;
3. verify tag peels to `expected_sha` and HEAD matches;
4. run the final portable battery/doctor/self-test;
5. run benchmark/claim/release-evidence commands;
6. validate required existing CI evidence for the same candidate SHA;
7. run legacy packaging/evidence where still required;
8. run the promotion gate;
9. publish prerelease for RC or final release only after PASS.

Concurrency must not cancel an in-progress release.

Commit: `ci: add evidence-gated v0.2.0 release workflow`

## Task 6 — Release-Candidate Dry Run

Create a candidate branch/tag only after green `main`. Use the release workflow with an RC tag such as `v0.2.0-rc.1` and exact expected SHA.

Validate:
- release workflow completes;
- prerelease is marked prerelease;
- evidence artifacts downloadable and non-empty;
- evidence hashes match candidate files;
- public docs do not describe RC as final;
- immutable v0.1.0 tag still peels to `accc50d727ef3d39d3929c4e4dd107e129e7d1a3`.

If any gate fails, fix through a normal PR, create a new RC candidate and never rewrite an already-published immutable evidence claim.

## Task 7 — Final v0.2.0 Promotion

Final promotion is allowed only when:

```text
portable runtime matrix              PASS
contracts/integration                 PASS
restart/recovery/idempotency          PASS
deterministic provider                PASS
browser/HUD smoke                     PASS
repository-scale context benchmark    PASS
resource measurement semantics        PASS
claim audit                           PASS
exact-SHA release evidence            PASS
v0.1.0 immutable target               PASS
```

Run the final release workflow with tag `v0.2.0`, exact SHA and `channel=final`. The workflow, not a manual force-update, creates/publishes release evidence.

After publication, verify release/tag/assets through GitHub APIs and re-check `main` CI. Only then update any “latest stable” wording if the workflow did not do so.
